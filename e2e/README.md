# E2E (Playwright)

Реальные браузерные проверки приложения против dev-сервера и **реального**
Supabase (`https://uwinrqeyixdnemszhxoj.supabase.co`, RLS включён).
Спеки только читают и навигируют: форм не отправляют, записи не делают,
под реальными аккаунтами не логинятся.

## Запуск

```bash
# установка один раз
npm.cmd install                      # devDependency @playwright/test
npx.cmd playwright install chromium  # браузер

# прогон (webServer поднимет `npm run dev` сам, если порт 5173 свободен)
npx.cmd playwright test --project=desktop-chromium
npx.cmd playwright test --project=mobile-chromium
npm.cmd run e2e          # все проекты
npm.cmd run e2e:ui       # интерактивный режим
```

Нужен работающий `.env.local` с `VITE_SUPABASE_URL` и
`VITE_SUPABASE_PUBLISHABLE_KEY` — иначе приложение покажет экран
«Supabase не настроен» и дымящий тест упадёт (это осознанно: без env
смёрсить нельзя).

Можно указать другой адрес: `E2E_BASE_URL=https://... npx.cmd playwright test`
(webServer при этом всё равно поднимает локальный dev-сервер).

## Почему e2e всегда анонимный (skip-причины больше нет)

Отложенная авторизация: ленту, фильтры и карточку объявления показываем без
сессии, вход нужен только на действиях («Подать объявление», «Мои», чаты,
профиль, «Написать автору», «Пожаловаться»). Поэтому:

- контентные спеки (`feed.spec.ts`, `listing-detail.spec.ts`) проверяют
  **реальную выдачу анонима** и больше не помечены `test.skip`;
- каждый спек сам фиксирует анонимный контекст —
  `test.use({ storageState: ANONYMOUS_STATE })` из `e2e/helpers.ts`, — так что
  результат не зависит от того, есть ли у машины сохранённая сессия;
- тестовый пользователь и `E2E_STORAGE_STATE` для e2e больше не нужны, опцию
  убрали из `playwright.config.ts`;
- экран входа проверяется через действия-гейты: клик по требующему входа
  действию обязан открыть форму с подсказкой («Войдите, чтобы …») и кнопкой
  «← Назад», а возврат — вернуть туда, откуда пришли (`auth-guard.spec.ts`,
  `listing-detail.spec.ts`).

## Что покрыто

- `feed.spec.ts` — дымок «/» открывается лентой без ошибок консоли; загрузка
  карточек (город `h3`, цена с «₽`, доступное имя кнопки-оверлея
  `Открыть объявление: <город>`, сверка с счётчиком «Всего: N»);
  фильтр «Тип = Сдают» — выдача завершается, бейдж «Сдаётся», фильтр не
  расширяет выдачу.
- `listing-detail.spec.ts` — клик по карточке → детальный экран («Назад»,
  «… ₽/мес.»), возврат в ленту; «Написать автору» и «Пожаловаться» у гостя
  ведут на вход с подсказкой и возвращают обратно (в чат не уводят, жалобу не
  отправляют).
- `auth-guard.spec.ts` — аноним на главной получает ленту, а не форму входа;
  форма входа (email/пароль/«Войти», переключение на регистрацию) открывается
  действием-гейтом «Профиль»; «Создать» и «Мои» открывают вход с подсказкой,
  «← Назад» возвращает в ленту.

Нюанс локаторов: подписи фильтров — `<span>` внутри `<label>`, поэтому
доступное имя `<select>` включает и текст опций («Тип Все Сдают Ищут»).
Точное `getByLabel('Тип', { exact: true })` в такое поле не попадёт — для этого
в помощниках есть `feedFilter(page, 'Тип')`.

## Что ловят помимо ассертов

Каждый спек собирает `console.error` и `pageerror` страницы (`e2e/helpers.ts`).
Исключения страницы и «значимые» console.error роняют тест; сетевой шум
(`Failed to load resource`: favicon, битые фото) выводится в аннотациях, но не
роняет. Цикл ре-рендеров, из-за которого приложение стояло колом, упал бы сюда
как `pageerror` («Maximum update depth exceeded») или как таймаут `openApp()` —
обе ситуации зелёным юнит-сьютом не ловились.

## Guard строгий: списка «известных дефектов» больше нет

После того как лента открылась анониму, спеки поймали две ошибки приложения
(вложенный `<button>` в карточке и CORS-ошибку edge-вызова `track-event` без
сессии) и на время были внесены в `KNOWN_APP_DEFECTS` как терпимые. Оба дефекта
исправлены в `src/**`, список удалён из `e2e/helpers.ts` целиком: теперь падает
любая `console.error`, кроме сетевого шума, и любой `pageerror`. Зелёный прогон
означает «в консоли браузера пусто», а не «пусто за вычетом оговорок» — сейчас
аннотаций `browser-error` в прогоне нет вообще.

Если такой шум появится снова, порядок действий: разобраться, откуда он
(дефект приложения, dev-сервер или реальные данные), и починить причину. Молча
заглушать его в e2e нельзя — иначе проверка превращается в декорацию.

## Разметка карточки и локаторы

`ListingCard` — это `<article>` (не `<button>`): текст читается скринридером, а
единственный интерактив — кнопка-оверлей `absolute inset-0` с доступным именем
`Открыть объявление: <город>`. Контролы карусели (стрелки `z-30`, точки в
оболочке `pointer-events-none`) лежат выше оверлея и забирают свои клики.
Поэтому:

- `listingCards(page)` ищет `getByRole('article')` с такой кнопкой внутри —
  прежний «`button`, содержащий `h3`» ничего бы не нашёл, ведь `h3` теперь вне
  кнопки;
- тесты кликают по карточке целиком (`cards.first().click()`): Playwright
  проверяет, что событие дошло до потомка статьи, то есть до оверлея, — если
  оверлей перестанет перекрывать карточку, тест упадёт на клике, а не «останется
  на ленте»;
- `feed.spec.ts` сверяет доступное имя оверлея с городом из `h3`
  (`toHaveAccessibleName`).

## Конфиг

`playwright.config.ts`: два проекта (`desktop-chromium` 1280×800,
`mobile-chromium` = Pixel 7), `trace: 'on-first-retry'`, `video: 'off'`,
retries 0 (флейки должны быть видны), воркеры по умолчанию (параллельность не
отключена).

Таймауты: `expect.timeout` 20с, `timeout` теста 60с. Причина — холодный старт:
пока Vite делает первую транспиляцию, три контекста одновременно грузят
приложение, и с 10с переключение формы входа в регистрацию в
`auth-guard.spec.ts` не успевало (при `--workers=1` тот же тест проходил за
<1с). Проверки это не ослабляет — ассерты те же, выросло только время
ожидания.

`e2e/global-setup.ts` перед стартом воркеров шлёт один GET на `baseURL` и ждёт
`HTTP 200` с каркасом приложения: dev-сервер прогревается, а недоступный сервер
падает здесь с описанием что проверять, а не «белым экраном» в каждом тесте.
